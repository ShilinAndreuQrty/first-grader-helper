# ADR 0001: модульный монолит с одним публичным origin

- Статус: принят
- Дата: 2026-07-29

## Контекст

Нужен production-ready MVP с SPA, API, очередью напоминаний, административным
интерфейсом и несколькими внешними интеграциями. Команда небольшая, данных и нагрузки
на старте немного, а часть контрактов ещё требует подтверждения.

## Решение

Использовать один репозиторий и модульный монолит:

- React 19 + TypeScript + Vite + VKUI 8;
- VK Bridge 3 и `@vkontakte/vk-mini-apps-router`;
- FastAPI + Pydantic + SQLAlchemy 2 + Alembic;
- PostgreSQL как единый источник истины;
- отдельный worker-процесс над той же моделью и таблицей заданий;
- Caddy и один публичный origin.

Интеграции оформляются портами/адаптерами. Реальная отправка уведомлений и AI-слой
выключены feature flags по умолчанию.

## Причины

- один origin упрощает защищённые cookie, CORS и VK WebView;
- модульный монолит дешевле сопровождать, чем микросервисы;
- PostgreSQL покрывает транзакции, очередь MVP, full-text и trigram-поиск;
- детерминированный retrieval объясним и достаточен для 60 исходных FAQ;
- адаптеры позволяют тестировать деградацию без обращения к внешним системам.

## Последствия

Положительные: простой локальный запуск, атомарные изменения данных, один пайплайн
деплоя, предсказуемые тесты. Отрицательные: worker и API масштабируются вместе на уровне
кода, а границы модулей поддерживаются соглашениями, а не отдельными сервисами.

Переход к брокеру сообщений, semantic search или отдельным сервисам рассматривается
только после появления измеримой нагрузки либо требований, которые PostgreSQL и один
процесс не покрывают.
